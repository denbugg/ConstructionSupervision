## Материалы организаторов

Организаторы выдают архив `7.ДГП_датасеты.zip` — это ресурсы из

| Что | Где | В git |

| `Строительная_техника.zip` — 100 снимков PNG | `ml/datasets/lct-raw/` | **нет**, 230 МБ |

Чтобы восстановить снимки на другой машине: распаковать вложенный `Строительная_техника.zip` в
`ml/datasets/lct-raw/` плоско, без вложенной папки. Имя папки внутри архива записано в кодировке
CP866, и без явной кодировки оно распаковывается нечитаемым.

### Что за снимки

- **Фото хода строительства, а не кадры с камер.** Около десятка разных московских объектов,
  сняты фотографом с рук или с крыш, в разных точках. Дата съёмки впечатана в кадр (2023–2026),
  между кадрами одного объекта — недели и месяцы.
- **Скриншоты, обрезанные вручную.** Размер плавает около 1080–1300 × 800–815 пикселей, EXIF нет.
- **Хорошие условия для проверки модели.** Лето и зима, котлованы, сваи, фундаменты, каркас;
  много буровых установок, экскаваторов, кранов, есть самосвалы, миксер, каток.

Для чего они годятся:
- тестовый набор распознавания и матрица ошибок ([docs/metrics.md](../docs/metrics.md), §2);
- проверка классификатора стадии по фото;
- материал для демо-хронологии, но с оговоркой ниже.

**Неподвижных камер в архиве нет.** Методика рассчитана на камеру, которая снимает с одной точки
раз в 20–30 минут. Для демо снимки собираются в хронологию вручную, как и предполагает ТЗ, п. 3:
1. **Точка съёмки — «камера».** Каждая точка съёмки заводится как отдельная камера (подпапка
   `cam-<код>`) со своими полигонами зон. Зоны разных точек связываются общей подписью участка
   ([ADR-0013](../docs/decisions/0013-zones-and-areas.md)), поэтому котлован, снятый с трёх
   точек, остаётся одним участком.
2. **Время — через имя файла.** Время задаётся именем файла `YYYYMMDD_HHMMSS`. Впечатанная дата
   распознаётся глазом и в систему не читается.
3. **Неподвижность не определяется.** У точки съёмки обычно нет «прошлого окна», поэтому
   `static = null`. Статус техники тогда определяется по зоне — базовым правилом заказчика
   ([methodology.md](../docs/methodology.md), раздел 6).
4. **Сценарий подстраивается под кадры.** Если сценарий из [runbook.md](../docs/runbook.md),
   раздел 6, не собирается из имеющихся кадров, правится сценарий, а не подделываются снимки.
   «Камера закрыта» показывается честно: точка съёмки, которая в этот день не прислала снимков
   (`NO_IMAGES`).

## reference/

Первоисточники, из которых собраны справочники сервисов. Держим их в репозитории, чтобы любое
число в системе можно было проверить по документу.

Правило: **каждая нормативная величина в коде и в справочниках сопровождается ссылкой на
источник** — документ, пункт, таблицу. Без ссылки число считается выдуманным. Нормы генератора
графика переносятся отсюда в `services/plan-service/data/mrr_norms.json`.

### Справочник работ: как он устроен на самом деле

Лист `Лист1`, 380 строк. Шапка — в строке 3: `№ п/п`, `Вид работ` и девять столбцов типов
объектов: `Жильё`, `Образование`, `Здравоохранение`, `Спорт`, `Культура`,
`Административные здания`, `ДОУ`, `Офисно-деловой центр`, `Дороги`. Правее шапки — пустые
столбцы.

Что учитывает парсер:
- **Коды строкой** — с точкой в конце: `10.`, `10.13.`, `10.14.2.`. Точка отбрасывается.
- **Коды, испорченные Excel,** приходят датами 2025 года. Правило общее: дата `d.m.2025` → код
  `d.m`. Так испорчено 19 кодов: `10.1`…`10.12` и `12.1`…`12.7`. Числа из ТЗ (`45667` → `10.1`
  и т. д.) — это те же даты в виде порядковых номеров Excel.
- **Код-число** `12` → `12`.
- **Строки без кода** (250 штук) — работы 4-го уровня внутри ближайшего кода сверху.
- **Отметка обязательности** — символ `˅` (U+02C5), пусто — не обязательно. Отметка не запрещает
  работу для других типов объектов (ТЗ, п. 1).

## seed/

```text
seed/
├── object.json         # демонстрационный объект и его параметры
├── schedule.xlsx       # календарный график с заложенными отклонениями
├── rules.json          # правила «этап → техника» для этапов графика без шаблона
├── cameras.json        # камеры (точки съёмки) и зоны на их эталонных кадрах
├── expected.json       # заложенные отклонения по дням: сверяет e2e.py, показывает demo.py
├── chronology.json     # какие серии датасета Лимы идут в какой демо-день
└── images/             # хронология снимков: cam-<код>/YYYYMMDD_HHMMSS.jpg (в git нет)
```

**Откуда кадры.** Демо строится на открытом датасете Universidad de Lima: четыре неподвижные
камеры одной стройки, снятые в разные дни ([ml/README.md](../ml/README.md), «Датасет Лимы»).
Снимки организаторов для этого не годятся, потому что неподвижных камер там нет (раздел выше).
В демо две камеры: `cam-torre-h` — обзорная с высоты, `cam-d3` — с земли у павильона D3.
`python scripts/seed_images.py` раскладывает их кадры по дням `chronology.json`, по одному на
30-минутное окно. Серия Лимы длится около 5 минут, в демо она растянута на рабочий день, и
даты демо (19–22.10.2026) условные. День, когда у камеры нет серии, — «камера закрыта».

**Готовые кадры** — архив `demo-images.zip` в релизе `demo-data-v1` на GitHub (CC BY 4.0,
авторство — Universidad de Lima, ссылка на датасет — ml/README.md). Его скачивает и распаковывает
в `images/` `python scripts/fetch_models.py`; собирает — `scripts/pack_assets.py`.

Порядок подготовки кадров с нуля: распаковать датасет в `ml/datasets/ulima/` (ml/README.md) →
`python scripts/seed_images.py` → `python scripts/seed.py` → зоны в редакторе интерфейса
(`/objects/<id>/settings/zones`) → `python scripts/export_zones.py` переносит их в
`cameras.json`, и следующий `seed.py` на чистом стеке соберёт объект уже с зонами.

- **График под кадры.** На кадрах Лимы здание уже в несколько этажей, поэтому в демо-дни по
  графику идёт только надземная часть: каркас 12.4.4 и бетонирование колонн и перекрытий
  12.4.10 (21–23.10). Засыпка пазух 12.3.10 закончена до демо (31.08–25.09). Этапа 12.4.10 нет
  в шаблоне этапов, поэтому его правило лежит в `rules.json`. Оно повторяет правило монолитного
  этапа 12.3.4 из таблицы ТЗ, п. 5.2: миксер и бетононасос.
- **Имена файлов.** Имя файла снимка — источник времени, если в EXIF его нет. Подпапка — код камеры.
- **Заложенные отклонения.** Демо-данные содержат заранее заложенные отклонения (D2, D3, D4, D10)
  и «нормальный день» 19.10 без D2 (только D4 на погрузчик у въезда). Сценарий по дням —
  [runbook.md](../docs/runbook.md), раздел 6. `scripts/e2e.py` проверяет, что система нашла
  именно их и не нашла лишнего.
- **Одна точка съёмки на камеру.** Зонная механика работает, только если все снимки одной
  подпапки сделаны с одной точки. Снимки с других точек — это другие «камеры».

### cameras.json

Координаты полигонов нормированы 0…1 от размера кадра (левый верхний угол — начало).
Одинаковые `zone_type` и `name` на разных камерах означают один участок
([ADR-0013](../docs/decisions/0013-zones-and-areas.md)).

```json
{
  "cameras": [
    {
      "code": "cam-north",
      "name": "Северная обзорная",
      "reference_image": "cam-north/20261020_090000.jpg",
      "zones": [
        {"zone_type": "PIT", "name": "Котлован", "polygon": [[0.09, 0.47], [0.30, 0.43], [0.33, 0.68], [0.08, 0.71]]},
        {"zone_type": "ENTRY_GATE", "name": "Въезд", "polygon": [[0.35, 0.48], [0.46, 0.44], [0.46, 0.74], [0.36, 0.74]]}
      ]
    },
    {
      "code": "cam-gate",
      "name": "Камера на въезд",
      "reference_image": "cam-gate/20261020_090000.jpg",
      "zones": [
        {"zone_type": "ENTRY_GATE", "name": "Въезд", "polygon": [[0.04, 0.45], [0.62, 0.40], [0.64, 0.95], [0.02, 0.95]]},
        {"zone_type": "STORAGE", "name": "Склад", "polygon": [[0.68, 0.35], [0.97, 0.33], [0.98, 0.80], [0.70, 0.82]]}
      ]
    }
  ]
}
```

Полигоны рисуют в редакторе зон интерфейса и переносят в файл `scripts/export_zones.py`.
