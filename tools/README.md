# tools — конфигурация инструментов

Общие настройки линтеров, форматтеров и CI, чтобы правила были одни на весь репозиторий,
а не семь разных.

| Файл | Что настраивает |
| :--- | :--- |
| `ruff.toml` | Линт и формат Python: правила, длина строки 100, порядок импортов |
| `requirements.txt` | Окружение хоста `.venv`: скрипты, ruff той же версии, что в CI, LabelMe (docs/runbook.md, раздел 3) |
| `mypy.ini` | *Ещё нет.* Проверка типов: нестрогий режим, строгий — на `core/` и `services/` |
| `eslint.config.js`, `prettier.json` | *Ещё нет.* Фронтенд — появятся вместе с `apps/web` |
| `.editorconfig` (в корне) | Отступы, переводы строк, кодировка |
| `../.github/workflows/` | GitHub Actions: линт → тесты → сборка образов (файлы лежат там, потому что GitHub читает только этот путь) |

Сервисы не переопределяют эти правила у себя. Нужно исключение — оно добавляется сюда
с комментарием, почему.

## Конвейер CI

`.github/workflows/ci.yml`, на каждый push в `main` и на каждый PR:

1. `discover` — находит сервисы: с `requirements.txt` их тестируют, с `Dockerfile` собирают.
2. `lint` — `ruff check` и `ruff format --check` по `packages`, `services`, `scripts`.
   Версия ruff закреплена и здесь, и в `requirements-dev.txt`: набор правил меняется между
   версиями, а неизвестный селектор роняет разбор `ruff.toml` целиком.
3. `test` — по джобу на сервис, параллельно, с настоящим PostgreSQL. Там же сверяется
   снапшот OpenAPI с кодом: нет снапшота — предупреждение, разошёлся — ошибка.
4. `build` — сборка образов, контекст у всех сервисов один: корень репозитория. На пуше
   в `main` образ ещё и уходит в ghcr с тегом `sha-<коммит>`; в PR только собирается.
5. `third-party` — на чистом раннере скачивает сторонние образы compose (Postgres, S3, Redis)
   и ждёт их готовности (`make third-party`). Пропавший из реестра образ краснит CI сразу,
   а не на чужой машине (ADR-0016).
6. `green` — один агрегирующий статус, чтобы в защите ветки не перечислять динамическую матрицу.
7. `promote` — только на пуше в `main` и только после `green`: ставит тег `main` на образы
   `sha-<коммит>`. `main` в реестре — всегда последний проверенный коммит.

`mypy`, `eslint` и `e2e` в конвейере пока нет: их добавляем, когда появится фронтенд и
`scripts/e2e.py` начнёт что-то проверять, — а не держим красными «на будущее».

`.github/workflows/release.yml` — релиз по тегу `v*` или вручную. **Ничего не собирает:** ждёт,
пока у коммита появится успешный статус «Всё зелено», и ставит тег версии и `latest` на его
образы `sha-<коммит>` (`docker buildx imagetools create`, секунды). Так в релиз попадают ровно
проверенные байты, а тег на красном коммите падает, а не публикует его. Сервисы находит тем же
способом, что `ci.yml`, по наличию `Dockerfile`.

Зачем сборка и публикация в одном конвейере: раньше Release собирал образы заново и CI не
ждал — тег на красном коммите уезжал на стенд, и опубликованное не было тем, что проверили.

| Тег в ghcr | Кто ставит | Что это |
| :--- | :--- | :--- |
| `sha-<коммит>` | `build`, каждый пуш в `main` | Кандидат; может быть и у красного коммита — сборка идёт параллельно с тестами |
| `main` | `promote` после `green` | Последний зелёный коммит `main` |
| `v0.x.y`, `latest` | Release | Точка отката для стенда; `latest` — последний релиз, а не последний коммит |

Теги `sha-*` копятся с каждым пушем; слои общие, поэтому место растёт на изменённые слои, но
список версий пакета стоит время от времени чистить в настройках пакета на GitHub.

## Когда CI нужно править

**Новый сервис конвейер не трогает вовсе.** Появился `requirements.txt` — его начинают
тестировать, появился `Dockerfile` — начинают собирать и публиковать. Перечислять сервисы
руками негде, и забыть строку невозможно: это сознательное решение, потому что забытая
публикация не красит конвейер и остаётся незамеченной.

Правка нужна в трёх случаях:

| Что произошло | Что поправить |
| :--- | :--- |
| Появился новый вид проверки (`mypy`, `eslint`, e2e) | новый job в `ci.yml` **и** соответствующая цель в `Makefile` |
| Изменилась версия линтера или Python | `ci.yml`, `requirements-dev.txt` сервисов, `tools/requirements.txt`, `tools/ruff.toml` — все, иначе локально и в CI разные правила |
| Сервису нужна своя внешняя зависимость в тестах (Redis, S3) | блок `services:` в джобе `test` |

Правило, из-за которого этот раздел существует: **локальный `make lint && make test` обязан
проверять ровно то же, что CI.** Разошлись — чинится не CI, а обе стороны сразу, иначе
локальная проверка перестаёт что-либо значить и все начинают отлаживаться пушами.
