# Правила разработки

Этот файл — **единственный свод правил** для всех, кто пишет код в этом репозитории.
Он главнее привычек, вкусов и «как обычно делают». Если правило мешает — правило меняется
в этом файле отдельным изменением, а не обходится молча.

Читать перед первой строкой кода: этот файл целиком → [docs/architecture.md](docs/architecture.md)
→ `README.md` того сервиса, который правишь.

---

## 1. Что мы строим

Система мониторинга строительной площадки по снимкам камер для Департамента градостроительной
политики г. Москвы (ЛЦТ 2026, кейс 07). Снимки с камер → распознавание техники и стадии объекта →
сравнение с календарным графиком → **объяснимые предупреждения** об отставании и нарушениях →
прогноз даты завершения этапов.

Три вещи, ради которых всё делается, в порядке важности:

1. **Бизнес-логика и объяснимость.** Заказчик прямо сказал: оценивается методика сопоставления
   план-факт, а не качество CV-модели. Каждое предупреждение обязано быть объяснено числами,
   правилом и снимками.
2. **Архитектура.** Новые типы техники, камер, объектов и планов должны добавляться **без правки
   кода**. Это отдельный критерий оценки, и он пронизывает весь дизайн.
3. **Готовность к интеграции.** Это не демо, а модуль чужой системы: REST API, Swagger, Docker,
   отсутствие скрытых связей между сервисами.

Мы не строим идеальную систему, мы строим честную, простую и цельную. Любое усложнение должно
окупаться в этих трёх пунктах.

## 2. Десять правил, которые не обсуждаются

1. **Сервисы общаются только по HTTP REST.** Никаких общих таблиц, общих файлов, общих очередей
   между сервисами, импортов чужого кода. Чужие данные берутся вызовом чужого API.
2. **У каждого сервиса с состоянием — своя база.** `plan-service` → `plandb`, `site-service` →
   `sitedb`, `analysis-service` → `analysisdb`. Один инстанс PostgreSQL, разные базы и разные
   пользователи. Межсервисные ссылки — **только по ID, без внешних ключей**.
3. **Конфигурация — данные, а не код.** Классы техники, зоны, правила «этап → техника», пороги
   отклонений, промпты, маппинг классов датасетов — в БД или в файлах справочников. В коде
   не должно быть ни одного захардкоженного порога, названия класса техники или срока.
4. **Каждое число объяснимо.** Любой расчёт, попадающий в предупреждение или прогноз, сохраняет
   исходные факты в поле `facts`. Если число нельзя объяснить — его не показываем.
5. **Доменная логика — чистые функции.** Всё, что в `src/core/`, не ходит в БД, не делает HTTP
   и не знает про FastAPI. Только вход → выход. Это то, что покрывается тестами и что мы
   показываем жюри.
6. **LLM не считает.** Модель получает готовую структуру фактов и пишет по ней текст со ссылками
   на ID отклонений. Ни одного числа LLM не генерирует. При недоступности LLM — шаблонный текст.
7. **Не знаешь — не выдумывай.** Нормативные значения (сроки, коэффициенты) берутся из
   первоисточников в `data/reference/` (МРР-3.2.81 — последняя редакция) и переносятся в
   справочники сервиса (`services/*/data/`) со ссылкой на пункт и таблицу. Придуманный
   «примерно такой» норматив — это брак, который завалит питч.
8. **Одна задача — один сервис.** Не правь одновременно несколько сервисов. Если изменение
   требует правок в двух — сначала меняется контракт (`packages/contracts`), потом поставщик,
   потом потребитель, отдельными коммитами.
9. **Ломать контракт нельзя.** В пределах `/api/v1` изменения только совместимые: добавить поле
   можно, убрать или переименовать — нет. Несовместимое изменение = новая версия пути.
10. **Готово = работает в `docker compose`.** Не «у меня локально». Любая задача считается
    сделанной только после того, как поднялась в общем стеке и прошла `make test`.

## 3. Карта репозитория: где что лежит

```text
services/<name>/          # backend-сервис = один Docker-контейнер
  src/main.py             #   точка входа FastAPI
  src/config.py           #   Settings (pydantic-settings), все переменные окружения
  src/api/routes/         #   роутеры: только валидация, вызов сервиса, маппинг ошибок
  src/api/schemas/        #   Pydantic DTO запросов и ответов (контракт наружу)
  src/core/               #   ЧИСТАЯ доменная логика: правила, расчёты, алгоритмы
  src/dal/                #   модели SQLAlchemy и репозитории (только здесь есть SQL)
  src/clients/            #   HTTP-клиенты к другим сервисам (только здесь есть httpx)
  src/services/           #   оркестрация: сценарии использования, транзакции
  src/worker.py           #   фоновый воркер (только site-service)
  migrations/             #   Alembic
  tests/                  #   pytest: unit на core/, api-тесты на routes
  data/                   #   статические справочники именно этого сервиса
  README.md               #   назначение, контракт API, модель данных, конфигурация
  Dockerfile, pyproject.toml

apps/web/                 # React SPA
packages/contracts/       # межсервисные контракты, классы техники, enum-ы, события, OpenAPI
packages/py-common/       # общая инфраструктура: логи, ошибки, health, http-клиент
packages/ts-api-client/   # TS-клиент, ГЕНЕРИРУЕТСЯ, руками не правится
docs/                     # архитектура, модель данных, методика, метрики, ADR
data/reference/           # первоисточники: справочник работ XLSX, выдержки МРР
data/seed/                # демо-данные: объект, график, камеры и зоны, снимки-хронология
data/models/              # веса моделей, в git не хранятся (make models)
ml/                       # офлайн-обучение детектора и оценка качества
scripts/                  # seed, demo, e2e, contracts, загрузка моделей
.github/workflows/        # CI: линт, тесты, сборка образов; публикация в ghcr
tools/                    # общие настройки линтеров и форматтеров
```

Сервисов четыре — `plan-service`, `site-service`, `analysis-service`, `vision-service` — плюс
`gateway`. Генератор графика живёт в plan-service, отчёты и LLM-резюме — в analysis-service
([ADR-0011](docs/decisions/0011-generator-and-reports-as-modules.md)). site-service только
описывает увиденное, все выводы делает analysis-service
([ADR-0012](docs/decisions/0012-facts-without-judgement.md)).

**Куда класть новый код:**

| Что добавляешь | Куда |
| :--- | :--- |
| Новый эндпоинт | `src/api/routes/<resource>.py` + схемы в `src/api/schemas/` |
| Новое правило, формулу, алгоритм | `src/core/<тема>.py`, чистой функцией, с тестом |
| Запрос к БД | `src/dal/repositories/<агрегат>.py` |
| Вызов другого сервиса | `src/clients/<service>_client.py` |
| Сценарий «получить A, посчитать B, сохранить C» | `src/services/<сценарий>.py` |
| Справочник, порог, шаблон текста | `data/` или таблица настроек, **не в код** |
| Класс техники | `packages/contracts/equipment_classes.yaml` |
| Изменение межсервисного контракта | сначала `packages/contracts/interservice.md`, потом код |
| Общая инфраструктурная утилита | `packages/py-common/` — и только если нужна ≥ 2 сервисам |

## 4. Команды

```bash
make up            # поднять весь стек
make pull          # забрать опубликованные образы из ghcr вместо сборки
make down          # остановить
make logs s=site   # логи одного сервиса
make seed          # загрузить демо-данные и прогнать анализ
make demo          # seed + сценарий показа (3 «дня» объекта)
make test          # тесты всех сервисов
make test s=plan   # тесты одного сервиса
make lint          # ruff: линт и проверка формата
make fmt           # автоформат
make dev           # стек с hot-reload (оверлей docker-compose.dev.yml)
make e2e           # сквозной сценарий на поднятом стеке
make contracts     # пересобрать снапшоты OpenAPI и TS-клиент
make migrate s=plan m="add stage_rule"   # создать миграцию
make health        # опросить /health всех сервисов
```

Перед тем как сказать «готово», обязаны пройти: `make lint`, `make test`, `make up && make health`.

**Windows.** На демо-стенде `make` запускает рецепты через cmd, где нет bash и grep, поэтому
цели Makefile там не работают. Команды-эквиваленты для PowerShell —
[docs/runbook.md](docs/runbook.md), раздел 3.

## 5. Рабочий цикл

**Перед задачей.**
Прочитай `README.md` своего сервиса и раздел [docs/architecture.md](docs/architecture.md) про него.
Проверь, не описан ли уже нужный контракт в `packages/contracts/interservice.md`. Если задача
требует нового сервиса, новой зависимости или несовместимого изменения API — **сначала ADR**
в `docs/decisions/`, потом код.

**Во время.**
Двигайся снизу вверх: чистая логика в `core/` с тестом → репозиторий → сценарий → роутер → UI.
Не пиши «на будущее»: ни абстрактных базовых классов с одним наследником, ни плагинных систем,
ни слоёв ради слоёв. Пиши так, чтобы соседний сервис читался как этот же сервис.

**Определение готовности (DoD).** Задача закрыта, когда:

- [ ] код проходит `make lint` и `make test`;
- [ ] чистая логика покрыта unit-тестами, эндпоинт — хотя бы одним api-тестом;
- [ ] `README.md` сервиса обновлён, если менялся контракт, модель данных или конфигурация;
- [ ] снапшот OpenAPI пересобран (`make contracts`), если менялся контракт;
- [ ] новые пороги/справочники вынесены в данные, а не оставлены в коде;
- [ ] в [docs/traceability.md](docs/traceability.md) отмечено закрытое требование ТЗ;
- [ ] сервис поднимается в общем `docker compose` и отвечает на `/health`.

## 6. Границы: что трогать нельзя

| Нельзя | Почему | Что делать вместо |
| :--- | :--- | :--- |
| Читать чужую БД, даже на чтение | Разрушает границу сервиса, ломает независимый деплой | Вызвать API владельца данных |
| Импортировать код из другого `services/*` | То же самое, плюс связность сборки | Продублировать 20 строк или вынести в `packages/py-common` |
| Складывать доменную логику в `packages/py-common` | Библиотека станет скрытым монолитом | Логика живёт в `core/` своего сервиса |
| Править `packages/ts-api-client` руками | Он генерируется | Поменять контракт и вызвать `make contracts` |
| Добавлять зависимость «просто удобнее» | Вес образа, риск сборки, время | Обосновать в PR или обойтись стандартной библиотекой |
| Заводить новый сервис | Каждый сервис — это compose, миграции, CI, документация | ADR с обоснованием, потом реализация |
| Хардкодить URL, порт, порог, класс техники | Ломает главный критерий оценки | `config.py` + `.env` или таблица настроек |
| Класть секреты в репозиторий | Очевидно | `.env`, который в `.gitignore` |

## 7. Правила API (кратко; полностью — [docs/api-guidelines.md](docs/api-guidelines.md))

- Путь: `/api/v1/<service>/<resource>` — префикс сервиса **один и тот же снаружи и внутри**,
  gateway ничего не переписывает. Примеры: `/api/v1/plan/objects`, `/api/v1/site/images`,
  `/api/v1/analysis/deviations`, `/api/v1/vision/analyze`.
- Ресурсы — существительные во множественном числе. Действие, не укладывающееся в CRUD, —
  под-ресурс с `POST`: `POST /api/v1/plan/objects/{id}/plan/generate`.
- Поля JSON — `snake_case`. Идентификаторы — UUIDv4 строкой. Время — ISO-8601 в UTC
  (`2026-10-20T09:00:00Z`), хранение `timestamptz`, показ пользователю — `Europe/Moscow`.
- Значения enum — `SCREAMING_SNAKE_CASE`, кроме классов техники: они `lower_snake_case`
  (`tower_crane`, `dump_truck`), потому что совпадают с метками CV-модели. Все enum-ы —
  в `packages/contracts/enums.yaml`, классы техники — в `packages/contracts/equipment_classes.yaml`.
  Дубликаты списков в коде запрещены; единственное исключение — CHECK-ограничения в моделях
  и миграциях БД.
- Списки: `?limit=&offset=` → `{"items": [...], "total": N, "limit": N, "offset": N}`.
- Ошибки: всегда `{"error": {"code", "message", "details", "request_id"}}`, `code` —
  стабильный `SCREAMING_SNAKE`, `message` — по-русски, для человека.
- `X-Request-Id` принимается, генерируется при отсутствии и передаётся во все вызовы дальше.
- Каждый сервис отдаёт `/health` (живой) и `/health/ready` (готов: БД, зависимости).

## 8. Правила кода (кратко; полностью — [docs/code-style.md](docs/code-style.md))

**Python 3.12, FastAPI, Pydantic v2, SQLAlchemy 2.0 (async), Alembic, httpx, pytest.**

- Всё асинхронное. Блокирующий вызов в обработчике — ошибка; тяжёлое (CV, PDF) — в воркер
  или в `run_in_threadpool`.
- Типы обязательны в сигнатурах публичных функций. Pydantic — на всех границах.
- Форматирование `ruff format`, линт `ruff`, длина строки 100.
- Имена: `snake_case` функции и переменные, `PascalCase` классы, `SCREAMING_SNAKE` константы.
  Английские идентификаторы, русские тексты для пользователя.
- Никакого `print`, только структурный логгер из `py-common`. Никаких «голых» `except`.
- Функция ≤ 50 строк, файл ≤ 400 строк — это ориентир, а не догма; превысил — подумай, почему.
- Ошибки: `core/` и `services/` бросают доменные исключения, `api/` переводит их в HTTP.

**TypeScript 5, React 18, Vite, TanStack Query, Tailwind.**

- `strict: true`. Никаких `any`. Типы API — только из `packages/ts-api-client`.
- Компонент не содержит бизнес-логики: вычисления — в хук или в `entities/`.
- Строки экрана можно писать в JSX (интерфейс только русский); общие строки — названия
  перечислений, тексты ошибок, единицы — в `src/shared/locale/ru.ts`.

## 9. Комментарии и документация

Это не формальность: «качество кода и документации» — отдельный критерий оценки,
а объяснимость — главный.

- **Комментарий отвечает на «почему», а не на «что».** `# увеличиваем счётчик` — мусор.
  `# берём максимум по камерам, а не сумму: зоны камер пересекаются, иначе двойной счёт` — норма.
- **Комментарии и докстринги — по-русски.** Код — по-английски.
- **Докстринг обязателен** у модуля, публичного класса и публичной функции: 1–3 строки о том,
  зачем это нужно. Параметры описываем, только если их смысл не очевиден из типа.
- **Нормативная ссылка обязательна** там, где есть число из документа:
  `# МРР-3.2.81, п. X.Y, табл. N: <что это за число>` — пункт и таблица последней редакции.
- **Ссылка на требование ТЗ** в шапке модуля, реализующего функцию из п.4 ТЗ:
  `"""Статусы техники: работает / простой / вне зоны (F4)."""`
- Запрещено: закомментированный код, `TODO` без имени и контекста, комментарии-заголовки
  вида `# ===== helpers =====`, повторяющие имя функции докстринги.
- `README.md` сервиса — часть кода. Меняешь контракт — меняешь README в том же изменении.
  Структура README сервиса фиксирована: назначение → место в системе → API → модель данных →
  конфигурация → зависимости → запуск и тесты.
- Архитектурное решение фиксируется ADR в `docs/decisions/NNNN-краткое-имя.md` по шаблону
  «Контекст → Решение → Последствия → Альтернативы». ADR не переписывают, его заменяют новым
  со статусом «отменяет ADR-XXXX».

## 10. Тесты

- Обязательны unit-тесты на всё в `src/core/`: правила отклонений, расчёт прогноза, CPM,
  привязку к зонам, парсер справочника. Это ядро продукта и единственное, что нельзя чинить
  «на демо».
- API-тесты через `httpx.ASGITransport`, БД — реальная в docker, фикстура на транзакцию.
- Внешние сервисы в тестах — заглушены; реальные вызовы только в e2e.
- E2E — `scripts/e2e.py`: поднять стек, прогнать демо-сценарий, проверить, что появились
  ожидаемые отклонения. Это же — регрессия перед релизом.
- Метрики CV (precision/recall/mAP по классам) считаются скриптом в `ml/` и попадают
  в `docs/` — их спросят.

## 11. Git

- Ветки: `feat/<service>-<кратко>`, `fix/<service>-<кратко>`, `docs/<кратко>`.
- Коммиты — Conventional Commits с областью-сервисом:
  `feat(site): привязка детекций к зонам по нижней точке bbox`,
  `fix(analysis): не дублировать D2 при повторном прогоне`.
- Один коммит — одно осмысленное изменение. Не смешивать рефакторинг с функциональностью.
- В `main` не коммитим ничего, что не поднимается в compose.
- Секреты, веса моделей, датасеты, `node_modules`, `*.pyc` — в `.gitignore`.
- Каждый PR проходит CI (`.github/workflows/ci.yml`): те же `make lint` и `make test`,
  плюс сборка образов и сверка снапшотов OpenAPI с кодом. Красный CI — не «потом починим»:
  в `main` он означает, что стек у соседа не поднимется.
- Сам конвейер правится редко и по понятному поводу — когда именно, перечислено
  в [tools/README.md](tools/README.md#когда-ci-нужно-править). Главное правило: `make lint`
  и `make test` обязаны проверять ровно то же, что CI; разошлись — правятся обе стороны.
- **Релиз — это тег.** Образы собирает и публикует CI на каждый пуш в `main`
  (`ghcr.io/<репозиторий>/<сервис>:sha-<коммит>`, после зелёного CI — ещё и `:main`).
  `git tag v0.2.0 && git push origin v0.2.0` запускает `.github/workflows/release.yml`:
  он ничего не собирает, а ставит `v0.2.0` и `latest` на образы этого коммита — только
  если CI на нём зелёный. Вручную — `gh workflow run Release` (только `latest`). Сервисы
  конвейер находит сам, дописывать их никуда не нужно.
- Зачем это нужно: на демо-ноутбуке `make pull` забирает готовые образы вместо сборки.
  Образ с CUDA собирается десятки минут — за час до показа этого времени нет.
  Подробности и вход в реестр — в [docs/runbook.md](docs/runbook.md), раздел 10.
- Теги ставит владелец репозитория, а не каждый по своему усмотрению: тег — это точка,
  на которую можно откатиться, и их не должно быть двадцать за день.

## 12. Чек-листы типовых задач

**Добавить класс техники** (должно обойтись без кода):
1. запись в `packages/contracts/equipment_classes.yaml`: код, название, группа, транзитность,
   промпты детектора, метки датасетов;
2. перезапуск `plan-service` и `vision-service`;
3. при необходимости — дообучение модели и новые веса;
4. упоминание класса в нужных правилах «этап → техника» через UI;
5. тест: правило с новым классом срабатывает.

**Добавить тип отклонения**:
1. описать в [docs/methodology.md](docs/methodology.md): код, условие, ключ, серьёзность, шаблон текста;
2. если условие выражается существующим предикатом — только запись в
   `services/analysis-service/data/deviation_rules.yaml` (предикат, параметры, шаблон текста),
   откуда она попадает в таблицу `deviation_rule`;
3. если нужен новый предикат — функция в `analysis-service/src/core/predicates.py`
   + регистрация в реестре + unit-тест на граничные случаи;
4. код отклонения — в `deviation_code` в `packages/contracts/enums.yaml`.

**Добавить эндпоинт**:
1. схемы запроса/ответа в `api/schemas/`;
2. сценарий в `services/`, чистая часть — в `core/`;
3. роутер, коды ошибок, описание в `README.md` сервиса;
4. `make contracts`, api-тест.

**Завести новый сервис** (только после ADR, см. раздел 6):
1. каталог по образцу `services/plan-service` — структура из раздела 3, `README.md` с контрактом;
2. `requirements.txt` и `Dockerfile` — по ним CI сам начнёт тестировать, собирать
   и публиковать сервис; конвейер править не нужно;
3. сервис в `docker-compose.yml` и в `SERVICES`, `NAME_*`, `PORT_*` в `Makefile`;
4. строка в `docs/architecture.md` и в карте раздела 3.

**Добавить таблицу**:
1. модель в `dal/models.py`, репозиторий в `dal/repositories/`;
2. миграция `make migrate`, проверка `upgrade` и `downgrade`;
3. описание в [docs/data-model.md](docs/data-model.md) и в README сервиса.

## 13. Если что-то непонятно

1. Ответ, скорее всего, уже есть: `docs/architecture.md`, `docs/methodology.md`,
   `packages/contracts/interservice.md`, `docs/api-guidelines.md`, ADR, README сервиса.
2. Нет ответа — выбери **самое простое решение, которое не нарушает правила раздела 2**,
   реализуй его и зафиксируй допущение: комментарием в коде и строкой в README сервиса
   в разделе «Допущения и ограничения».
3. Решение затрагивает границы сервисов, контракт или стек — не решай молча, заведи ADR.
4. Никогда не придумывай нормативные числа, метрики моделей и результаты тестов.
   Нет данных — так и пиши: «не измерено».
