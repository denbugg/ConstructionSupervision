# contracts — контракты системы

Единственный источник истины по тому, о чём сервисы договорились между собой.
Меняется раньше кода, а не после.

## Состав

```text
contracts/
├── interservice.md         # межсервисные контракты: план, факты, распознавание, прогон
├── equipment_classes.yaml  # классы техники — единственный источник (ADR-0014)
├── enums.yaml              # канонические перечисления, роли и названия типов зон, порядок стадий
├── events.md               # доменные события: имена и полезная нагрузка
└── openapi/                # снапшоты OpenAPI каждого сервиса (коммитятся, появляются с кодом)
    ├── plan-service.json
    ├── site-service.json
    ├── analysis-service.json
    └── vision-service.json
```

`equipment_classes.yaml` и `enums.yaml` монтируются в контейнеры только для чтения
(`./packages/contracts:/contracts:ro`, переменная `CONTRACTS_DIR`). Сервис читает их при
старте, поэтому правка файла требует перезапуска, но не пересборки образа.

## Как это работает

1. Сначала меняется `interservice.md`. Несовместимое изменение согласуется через ADR.
2. Разработчик меняет схемы в сервисе-поставщике, потом в потребителе.
3. `make contracts` перегенерирует снапшоты OpenAPI и TS-клиент.
4. CI сравнивает снапшот в репозитории с тем, что отдаёт код. Нет снапшота — предупреждение,
   расхождение — ошибка сборки.

Смысл: изменение контракта невозможно протащить незаметно. Оно всегда видно в диффе,
и его всегда видит потребитель.

## Правила изменения

- Добавить поле в ответ или значение в перечисление можно. Потребитель игнорирует
  неизвестные поля.
- Удалить или переименовать поле или значение — **несовместимое изменение**, требует ADR и `v2`.
- Изменение контрактов «весь план» и «факты за период» — только через ADR: на них
  завязана вся методика.
- Добавить класс техники — запись в `equipment_classes.yaml`, без ADR.
