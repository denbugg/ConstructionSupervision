# Аудит проекта: архитектура, документация, реалистичность

Дата: 19.09.2026. Сдача: 29.09. Осталось 10 дней. Ресурсов на дообучение и на «сделать всё» нет.

Аудит смотрел на всё, что есть в репозитории: 46 markdown-файлов, 10 ADR, восемь README
сервисов, каркасы четырёх сервисов, compose, CI, py-common, SPA.

---

## 1. Резюме

1. **Документация описывает готовый продукт, код описывает первую неделю.** 442 КБ markdown
   против 92 КБ исходного Python (из них половина — модели и миграции). Реально работает один
   эндпоинт: CRUD объектов в `plan-service`. Остальное — каркасы с `/health`.
2. **Рубеж T0 «к 20.09» невыполним.** Он требует генерации плана (нет `pos-engine`),
   распознавания (в `vision-service` нет модели), анализа D1/D2 (в `analysis-service` нет
   ни одной функции), демо-данных (`seed.sh` — заглушка) и UI (один пустой экран).
3. **Главная опасность — `pos-engine`.** Это самый большой документ репозитория (597 строк),
   описывающий сервис, которого в репозитории нет ни в одном коммите. При этом заказчик
   в ТЗ прямо сказал: ПОС не нужен. Нормативный движок с ТСН, КСР, 299-ПП и Законом № 42 —
   работа на две недели, которую никто не оценит.
4. **Архитектура правильная по идее и тяжёлая по исполнению.** Разрез «план / факт / сверка»,
   правила как данные, объяснимость через `facts` и `evidence`, честный `UNKNOWN` — всё это
   стоит сохранить. Но 7 сервисов, 3 базы, 3 набора миграций, Redis, arq, MinIO, Ollama,
   генерация TS-клиента и снапшоты OpenAPI — это инфраструктура для команды из 8 человек
   на 2 месяца, а не для «около нуля ресурсов» на 10 дней.
5. **Что делать:** свернуть backend в два контейнера (`api` + `vision`), оставить одну базу,
   выбросить очередь и объектное хранилище из MVP, сократить методику до 6 отклонений,
   сжать документацию в 6 файлов и переписать план на 10 дней от текущего состояния.

Всё остальное ниже — обоснование этих пяти пунктов и конкретный список правок.

## 2. Что сделано хорошо и что нужно сохранить

Это не формальный раздел. При упрощении легко выплеснуть то, ради чего проект стоит.

| Что | Почему это ценно |
| :--- | :--- |
| **`docs/methodology.md`** | Единственный документ, который жюри будет читать целиком. Цепочка «снимок → зона → статус → сессия → факт → отклонение → прогноз» связная, каждое число объяснимо, слепая зона не считается пустой, есть `UNKNOWN` и `confidence`. Это и есть продукт |
| **Правила как данные** (`stage_rule`, `deviation_rule`) | Прямое закрытие критерия «расширение без правки кода». Демо «меняем минимум самосвалов — D2 исчезает» заменить нечем |
| **Инвариант `facts` + `evidence`** | Каждое отклонение обязано нести числа и снимки. Это то, что отличает продукт от демо |
| **`packages/py-common`** | Компактно и грамотно: конверт ошибок, `X-Request-Id`, health с необязательными проверками, ретраи только для идемпотентных методов. Не трогать |
| **Каркас `plan-service`** | Слои чистые, `core/calendar.py` — образец, тесты идут через миграции на настоящем PostgreSQL, проверяется `downgrade`, сценарии тестов названы по-русски. Копировать именно это |
| **Миграции** | `text + CHECK` вместо enum, частичный уникальный индекс с `NULLS NOT DISTINCT` для дедупликации отклонений — решения продуманные |
| **Зоны в координатах кадра 0…1, без PostGIS** | Верно. Простая проверка «точка в полигоне», разметка не зависит от разрешения |
| **Отказы** (нет брокера, нет k8s, нет своих пользователей) | Зафиксированы явно и с аргументами |
| **CI находит сервисы сам** | Одно правило на всех, ничего не перечисляется руками |
| **Разделы «Реализовано на сегодня»** в README | Честно. Без них документация была бы враньём |

## 4. Логические дыры и несостыковки

Это не опечатки, а места, где методика или границы не сходятся.

1. **`is_working_time` считается в `site-service`, а календарь лежит в `plan-service`.**
   Методика §2: «рабочая сессия — целиком в рабочем времени календаря объекта». Поле стоит
   в `sitedb.session` и в контракте `/sessions/{id}/facts`. Но по архитектуре §6
   `site-service` вызывает только `vision-service`. Кто заполнит поле — не определено.
   При одном сервисе проблема исчезает сама.
2. **`progress_cap_по_стадии` «задаётся в справочнике»** (методика §9.3). Ни в одной таблице
   `data-model.md` такого справочника нет.
3. **API-ключ лежит в бандле SPA.** `apps/web/src/shared/api/client.ts` подставляет
   `VITE_API_KEY ?? "dev-key-change-me"`. Любой, кто открыл интерфейс, видит ключ.
   ADR-0010 при этом описывает ключ как защиту периметра. Для MVP это нормально, но надо
   написать честно: ключ защищает API от случайного вызова, а не от пользователя интерфейса.
4. **Материализованный `session_fact` и машина состояний сессии** (`OPEN → CLOSED → AGGREGATED`,
   `SESSION_CLOSE_GRACE_MINUTES`, задача `aggregate_session`, сигнал в `analysis`) —
   при этом `analysis-service` объявлен «полностью пересчитываемым с нуля». Если сверка
   и так всё пересчитывает, агрегат сессии можно считать на лету из детекций одним запросом.
   Вся машина состояний, grace-период и «сигнал пересчёта» тогда не нужны.
5. **Пороги методики живут в двух местах**: `.env` (`MIN_ACTIVITY`, `ON_TRACK_TOLERANCE_DAYS`,
   `MOVE_THRESHOLD`) и таблица `deviation_rule.params`. Runbook это признаёт словом
   «продублированы». Один источник: таблица, `.env` только для первичного заполнения.
6. **Нефункциональные требования обещают 8–15 мс на GPU для YOLO `s`**, а детектор по
   умолчанию — YOLO-World, у которого в том же README 30–200 мс. Обещание и дефолт расходятся.
7. **`pos-engine` описан как «HTTP-обёртка над существующим движком»** (`board.md`, `A-05`).
   Движка в репозитории нет ни в одном коммите. Если он существует вне репозитория —
   это нужно проверить сегодня, а не 25-го. Если нет — это не задача на день.
8. **Правило 7 AGENTS.md «не выдумывай нормативы»** против README `pos-engine`, где приведены
   коды КСР (`02.01.01-035`), машино-часы ТСН (`3680.0`) и коэффициенты без ссылок на
   таблицу и страницу. Проверить это некому и некогда. Всё, что нельзя показать в документе,
   надо убрать из ответа API, иначе первый же вопрос жюри «откуда 3680» станет последним.
9. **Классификация стадии по фото (F6, D7, ограничение прогресса)** — вторая модель
   (OpenCLIP, ~0.6 ГБ), свой набор промптов, свой справочник «стадия → максимальный прогресс»,
   правило подтверждения ≥ 2 сессий. Это отдельный подпроект, на который завязано ещё одно
   отклонение и формула прогресса. При «около нуля ресурсов» его надо отвязать от ядра.

## 5. Архитектура: что упростить

### 5.1. Что не даёт ни балла

Критерий «архитектура» в ТЗ сформулирован так: *новые типы техники, камер и планов без
переделки кода*. Это про данные, а не про количество контейнеров. Микросервисы жюри не
просило, и модуль в чужую ИС — это в первую очередь API и Docker-образ, а не семь образов.

| Элемент | Стоимость сейчас | Что даёт | Решение |
| :--- | :--- | :--- | :--- |
| 3 сервиса `plan` / `site` / `analysis` с 3 базами | 3 Dockerfile, 3 alembic, 3 README, 3 набора тестовых фикстур, HTTP-клиенты и фикстуры контрактов между ними, две «ключевые» агрегирующие ручки | Параллельная работа треков, которых нет | **Один сервис `api`, одна база, три пакета `plan/`, `site/`, `analysis/` внутри.** Границы сохраняются как границы модулей: `analysis` импортирует только публичные функции `plan` и `site`, не их модели. Это проверяется ревью, а не сетью |
| `pos-engine` как сервис | Отдельный контейнер, README на 597 строк, 6 движков, 4 нормативные базы | Генерацию графика из названия объекта | **Модуль `plan/core/schedule_template.py`**: шаблон WBS на 12 вех из ТЗ §5.2, доли длительности по фазам из одной таблицы МРР, правила техники из той же таблицы ТЗ. Около 200 строк и один JSON. Парсер названия — три регулярных выражения (этажность, «монолит», «дорога») |
| `report-service` | Отдельный контейнер, WeasyPrint, Jinja2, LLM-клиент, бакет `reports` | PDF и резюме | **Модуль `report/` в `api`**: одна HTML-страница отчёта, PDF через WeasyPrint в том же процессе, файл в локальный том. LLM — последним пунктом плана, если останется день |
| Redis + arq + `site-worker` | Контейнер, зависимость, конфиг воркера, отдельная команда запуска | Фоновая обработка снимков | **Цикл-опрос в процессе `api`**: раз в 2 секунды берёт снимки со `status=PENDING`, гонит в `vision`, пишет детекции. Источником истины `image.status` уже объявлен, значит очередь и так не нужна. 40 строк |
| MinIO | Контейнер, boto3, presigned-ссылки, инициализация бакетов | Хранение снимков | **Локальный том**, отдаётся nginx по `/media/`. Один класс `Storage` с двумя методами, чтобы S3 у заказчика был заменой класса. ADR-0005 останется верным как «дальнейшее развитие» |
| Ollama, профиль `llm` | Секция compose, том, документация | Закрытый контур | Убрать из compose и документации. Одно предложение в разделе «развитие» |
| CUDA-образ `vision-service` | 6–8 ГБ, десятки минут сборки, `nvidia-container-toolkit`, отдельный workflow публикации в ghcr | Миллисекунды вместо секунд | **CPU по умолчанию**: `torch` CPU-сборка, образ ~1.5 ГБ. 70 демо-снимков × 1–2 с — две минуты, и они прогоняются заранее. GPU — опция для того, кто захочет |
| Снапшоты OpenAPI в CI + генерируемый TS-клиент | Скрипт, проверка в CI, пакет `ts-api-client`, правило «типы только оттуда» | Защиту от рассинхрона контрактов | При одном сервисе рассинхронизироваться не с кем. Типы для фронта — `openapi-typescript` один раз руками, файл коммитится. Проверку в CI убрать |
| Ревизии плана с полными снимками (`plan_revision`) | Таблица, логика, эндпоинт истории | Аудит бюджетного объекта | Оставить таблицу, писать одну строку при правке. Эндпоинт истории и UI не делать |

### 5.2. Целевая картина

```
docker compose:
  gateway   nginx: SPA + /api → api, /media → том снимков          (есть)
  api       FastAPI: plan | site | analysis | report, одна БД lct   (собрать из трёх каркасов)
  vision    FastAPI + ultralytics, CPU, YOLO-World по промптам       (дописать)
  postgres  одна база, одна роль, один alembic
```

Четыре контейнера вместо двенадцати. Всё, что было правильного в разрезе, остаётся
внутри `api` как структура пакетов:

```
services/api/src/
  plan/      objects, stages, rules, calendar, schedule_template, import_xlsx
  site/      cameras, zones, images, detections, worker (опрос PENDING)
  analysis/  core/: matching, predicates, activity, forecast, explain; run
  report/    html + pdf, summary (шаблон; LLM опционально)
  main.py, config.py, db.py, migrations/
```

Правило AGENTS.md «доменная логика — чистые функции в `core/`» остаётся главным.
Правило «сервисы общаются только по HTTP» заменяется на «модули общаются через публичные
функции, не через чужие таблицы». Это та же дисциплина без сетевого налога.

**Если команда всё-таки из трёх backend-разработчиков и каждый хочет свой сервис** —
разрез `plan / site / analysis` можно оставить. Тогда обязательно: одна база с тремя схемами
вместо трёх баз (меньше DSN, ролей и скриптов), `pos-engine` внутрь `plan`, `report`
внутрь `analysis`, без Redis и без MinIO. Но по формулировке «ресов около 0» это не ваш случай.

### 5.3. Упрощения внутри методики, не ломающие её смысл

| Сейчас | Проще | Что теряется |
| :--- | :--- | :--- |
| Сессия — сущность с состояниями, grace-периодом и агрегацией | Сессия — `floor(captured_at, 30 мин)`, вычисляется запросом | Ничего: прогон анализа всё равно пересчитывает всё |
| `zone_visibility` с `coverage` по площади и статусом `PARTIAL` | `BLIND`, если в сессии нет ни одного пригодного кадра с камеры этой зоны; иначе `OK` | Статус `PARTIAL`. Его никто не покажет и не объяснит за 5 минут демо |
| `overlaps_with` между зонами разных камер | Максимум по камерам считается по паре `(zone_type, класс)` на объект | Различение двух зон одного типа. В демо одна площадка |
| Ограничение прогресса стадией по фото | Прогресс только по активности техники; стадия по фото — отдельная строка в UI «по фото: котлован (0.78)», если успели | Защита от «техника работает, здание не растёт». Честно написать в ограничениях |
| Перенос задержки по графу связей FS/SS/FF с лагами | Сдвиг только по цепочке FS следующих вех | SS/FF. В шаблоне WBS их и нет |
| D1–D10 | **D1, D2, D3, D4, D9, D10** — в демо-сценарии участвуют D2, D3, D4, D10; D1 и D9 дешёвые. D8 добавить, если останется полдня | D5 (почти дубль D3), D6 (Could в ТЗ), D7 (нужна стадия по фото) |
| Эскалация серьёзности по дням | Одна серьёзность на код из `deviation_rule` | Рост серьёзности. Никто не заметит |

Что **нельзя** резать: `facts` и `evidence` у каждого отклонения, `/explain`, редактор правил
в UI, статус `UNKNOWN`, слепая зона ≠ пустая, `confidence` у прогноза. Это ответы на вопросы,
которые точно зададут.

## 6. Документация: перегружена и дублируется

### 6.1. Диагноз

- 46 файлов, 442 КБ. Один только `pos-engine/README.md` больше, чем весь `py-common`.
- **Дублирование.** Таблица сервисов повторена в `README.md`, `AGENTS.md` §3,
  `docs/README.md`, `architecture.md` §3, `runbook.md` §9. Правила API — в `AGENTS.md` §7
  и `api-guidelines.md`. Правила кода — в `AGENTS.md` §8–9 и `code-style.md`. Переменные
  окружения — в `.env.example`, `runbook.md` §4 и в README каждого сервиса. Пример «план
  на дату» — в `api-guidelines.md` §11.1 и `plan-service/README.md`. Модель данных —
  в `data-model.md`, в докстрингах `models.py` и в миграциях.
- **Спекулятивные контракты.** README сервисов описывают по 15–20 эндпоинтов, которых нет.
  Через неделю половина будет выглядеть иначе, и README придётся переписывать вместо кода.
- **Процесс тяжелее команды.** Доска + роадмап + матрица трассируемости + DoD из 7 пунктов +
  шаблон PR из 10 галочек + ADR на любое изменение границ + «задачу назначает человек» —
  это процесс для отдела. Для 1–3 человек на 10 дней он стоит часов в день.
- **Глоссарий, стиль кода, стратегия тестирования, ADR** — хорошие тексты, но каждый из них
  читается один раз и потом не поддерживается. `ruff` уже обеспечивает стиль; тесты в
  `plan-service` уже показывают, как писать тесты.
