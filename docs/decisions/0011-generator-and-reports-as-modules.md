# ADR-0011. Генератор графика и отчёты — модули, а не сервисы

**Статус:** принято, 23.09.2026. Частично отменяет [ADR-0002](0002-service-boundaries.md):
из трёх «знаний без данных» отдельным сервисом остаётся только `vision-service`.

## Контекст

ADR-0002 вынес в отдельные сервисы `pos-engine` (нормативный расчёт графика) и
`report-service` (PDF и LLM-резюме). К 23.09 ни один из них не написан. До сдачи шесть дней.

- `pos-engine` задумывался как генератор графика по нормативам (ТЗ, п. 8), чтобы было
  к чему привязывать снимки. Его README разросся до полного ПОС: подбор марок машин по КСР,
  буфер ОАТИ по 299-ПП, окна тишины по закону № 42. Заказчик прямо назвал ПОС ненужным
  (ТЗ, таблица Q&A), и по критериям оценки эти функции баллов не дают.
- `report-service` ничего не считает сам. Он оформляет данные `analysis-service` и
  `plan-service` и для этого держал бы три HTTP-клиента.
- Каждый отдельный сервис — это контейнер, запись в compose, клиенты с таймаутами, README,
  маршрут в gateway и ещё одна точка отказа на демо.

## Решение

- **Генератор графика — модуль `plan-service`:** `src/core/schedule_generator.py`, нормы и
  шаблоны этапов в `services/plan-service/data/`. Вход — тип объекта и параметры (этажность,
  площадь, секции, сваи, сменность, дата начала). Выход — этапы с датами, связями, критическим
  путём и правилами «этап → техника» из шаблона. Всё, что не нужно ТЗ, не переносится:
  КСР, 299-ПП, закон № 42, разбор наименования объекта.
- **Отчёты и LLM-резюме — модуль `analysis-service`:** `src/report/`, эндпоинты
  `/api/v1/analysis/reports` и `/api/v1/analysis/summary`. Правила LLM из
  [ADR-0008](0008-llm-narrative-only.md) не меняются.
- В системе четыре своих сервиса (`plan`, `site`, `analysis`, `vision`) и `gateway`.
  `vision-service` остаётся отдельным: torch и GPU — единственная граница, которая точно
  окупается.

Где теперь живут данные, которые ADR-0007 относил к упразднённым сервисам:

| Что | Где |
| :--- | :--- |
| Нормативы сроков и шаблоны этапов | `services/plan-service/data/mrr_norms.json`, `wbs_templates.json` |
| Тексты предупреждений D1–D10 | `deviation_rule.message_template`; начальные значения — `services/analysis-service/data/deviation_rules.yaml` |
| Промпты LLM | `services/analysis-service/prompts/*.md` |

## Последствия

**Хорошо:** в compose девять контейнеров вместо одиннадцати. Два межсервисных контракта и
четыре HTTP-клиента не нужно ни писать, ни отлаживать. Генератор и сборка отчёта
тестируются как чистые функции в `core/` своих сервисов.

**Плохо:** образ `analysis-service` тяжелеет на WeasyPrint и его системные библиотеки.
Если отчёты понадобится масштабировать отдельно, модуль выносится обратно в сервис: gateway
может направить `/api/v1/analysis/reports` на другой апстрим, и клиенты этого не заметят.

## Альтернативы

- **Оставить оба сервиса.** Дороже на шесть дней работы и не добавляет баллов ни по одному
  критерию.
- **Модульный монолит целиком.** Проще с нуля, но каркасы трёх сервисов, их миграции и CI
  уже готовы: переписывание не окупится до сдачи.
