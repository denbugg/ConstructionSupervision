# ADR-0014. Классы техники — один файл

**Статус:** принято, 23.09.2026. Отменяет в [ADR-0007](0007-rules-as-data.md) строку
«Классы техники и алиасы датасетов — `plandb.equipment_class`, правит оператор через UI».

## Контекст

Классы техники были описаны в четырёх местах:
- `equipment_class_seed` в `enums.yaml`;
- таблица `plandb.equipment_class`;
- `class_map.yaml` в vision-service;
- `class_map.yaml` в `ml/prepare`.

При этом в одном поле `aliases` смешивались два разных понятия: текстовые промпты детектора
и метки внешних датасетов. А класс, добавленный оператором через интерфейс, детектор не
видел бы вовсе: vision-service читает свой файл, а не базу plan-service.

## Решение

- `packages/contracts/equipment_classes.yaml` — единственный источник классов. У каждого
  класса есть код, название, группа, признак транзитности, промпты детектора и метки
  внешних датасетов.
- Файл монтируется в контейнеры только для чтения.
  - plan-service отдаёт классы через `GET /api/v1/plan/equipment-classes` и проверяет по
    ним коды в правилах этапов.
  - vision-service берёт из файла промпты.
  - `ml/` берёт метки датасетов.
  - analysis-service получает классы в контракте «весь план».
- Таблица `plandb.equipment_class` удаляется. Классы в интерфейсе доступны только для чтения.

## Последствия

**Хорошо:**
- Добавить класс — одна правка файла и перезапуск plan-service и vision-service. Критерий
  «новые типы техники без переделки кода» выполняется честно, и это можно показать на демо.
- Промпты и метки датасетов больше не путаются.

**Плохо:**
- Оператор не может добавить класс из интерфейса, нужен доступ к файлу. Для хакатона и
  для установки у заказчика это допустимо: классы меняются редко и вместе с моделью.

## Альтернативы

- **Классы в базе plan-service, а vision запрашивает их у plan.** Появляется связь
  vision → plan, и распознавание перестаёт быть независимой чистой функцией.
- **Классы в базе, а в vision ручная синхронизация.** Именно так было раньше, и именно
  отсюда четыре копии.
