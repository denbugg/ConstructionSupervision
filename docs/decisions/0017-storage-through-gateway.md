# ADR-0017. Хранилище для браузера — через gateway

**Статус:** принято, 28.09.2026. Уточняет [ADR-0005](0005-object-storage.md) и
[ADR-0016](0016-seaweedfs-instead-of-minio.md): presigned-ссылки остаются, меняется адрес,
по которому их открывает браузер. Переменная `S3_PUBLIC_ENDPOINT` заменена на `S3_PUBLIC_PATH`.

## Контекст

Ссылки на снимки и отчёты подписывались на `S3_PUBLIC_ENDPOINT=http://localhost:8333`. На
машине стенда это работало, но стоило открыть интерфейс с другой машины — из локальной сети,
через Tailscale или Cloudflare Tunnel, — как не грузилась ни одна картинка и ни один PDF:
браузер шёл в `localhost` своей машины. Подписать на «правильный» адрес заранее нельзя:
у одного стенда их несколько сразу, а туннель ещё и отдаёт интерфейс по HTTPS, и ссылка
на `http://…:8333` блокируется как смешанное содержимое. Открывать наружу второй порт ради
хранилища — лишняя настройка сети на каждом стенде.

## Решение

Хранилище отдаётся браузеру через gateway, по тому же адресу, что и интерфейс.

- Сервисы подписывают ссылку для браузера на внутренний адрес `S3_ENDPOINT` (`s3:8333`),
  как для соседних сервисов, и отдают из неё только путь с параметрами под префиксом
  `S3_PUBLIC_PATH`: `/storage/images/…?X-Amz-…`. Хоста в ссылке нет — браузер открывает её
  относительно адреса, по которому пришёл.
- gateway (`location /storage/`) отрезает префикс и передаёт запрос в `s3:8333` с
  `Host: s3:8333`. Путь и параметры берутся из `$request_uri` без раскодирования. Подпись S3
  покрывает `Host`, путь и параметры, поэтому она сходится.
- Заголовки `X-Forwarded-*` и `Forwarded` хранилищу не передаются: SeaweedFS учитывает их
  при проверке подписи, а туннель их ставит.

Python-сервисы байты по-прежнему не проксируют: это делает nginx, как и со статикой SPA.

## Последствия

**Хорошо:** интерфейс работает с любого адреса стенда без настройки; наружу нужен один порт
gateway; HTTPS туннеля распространяется и на снимки; кнопка «Скачать» у отчёта скачивает файл,
а не открывает его, — атрибут `download` работает только для ссылок того же адреса.

**Плохо:** картинки идут через gateway — ещё один переход, заметный разве что на пакетах из
сотен снимков. Хост в `proxy_set_header Host` gateway и в `S3_ENDPOINT` сервисов должен
совпадать — это связь через конфигурацию, описанная в README gateway и runbook. Ссылка
в ответе API стала относительной: внешняя система открывает её от адреса gateway, по
которому вызывала API. Старая переменная `S3_PUBLIC_ENDPOINT` в `.env` больше ничего не
значит и её можно удалить.

## Рассмотренные альтернативы

- **Прописать в `S3_PUBLIC_ENDPOINT` IP стенда в сети.** Работает для одного адреса: Tailscale
  и туннель остаются без картинок, а туннель по HTTPS блокирует ссылку на HTTP.
- **Подписывать ссылку на адрес из заголовков запроса (`Host`, `X-Forwarded-Host`).** Адрес
  становится верным, но хранилище по-прежнему надо открыть наружу отдельным портом и отдельным
  туннелем, а сервисы начинают доверять заголовкам, которые подставляет клиент.
- **Отдавать байты снимков эндпоинтом сервиса.** Работает везде, но нагружает Python-процессы
  раздачей картинок — ровно то, от чего уберегал ADR-0005.
