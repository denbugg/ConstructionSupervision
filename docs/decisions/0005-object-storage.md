# ADR-0005. Снимки в объектном хранилище, а не в базе

**Статус:** принято, 17.09.2026. Бакеты `previews` и `reference` не используются: рамки
рисуются поверх снимка, эталонный кадр — один из снимков
([architecture.md](../architecture.md), раздел 7.2). Сервер хранилища в стенде — SeaweedFS
вместо MinIO ([ADR-0016](0016-seaweedfs-instead-of-minio.md)).

## Контекст

Камеры по периметру, снимок раз в 20–30 минут, круглосуточно. Даже один объект с четырьмя
камерами даёт ~200 снимков в сутки; архив организаторов — до 200 МБ. Снимки нужны как
доказательства в предупреждениях, то есть отдаются пользователю часто.

## Решение

MinIO (S3-совместимое хранилище). В БД — только метаданные и ключ объекта.
Бакеты: `images` (оригиналы), `previews` (превью и кадры с рамками), `reference`
(эталонные кадры камер), `reports`.

Ключ: `{object_id}/{camera_id}/{YYYY-MM-DD}/{image_id}.jpg` — по префиксу видно объект,
камеру и дату, выборочная выгрузка тривиальна.

Наружу снимки отдаются **presigned-ссылками** с TTL: ни один сервис не проксирует
байты изображений через себя.

## Последствия

**Хорошо:** база остаётся маленькой и быстрой; бэкап метаданных отделён от бэкапа
изображений; замена MinIO на любой S3 заказчика — смена переменных окружения;
раздача картинок не нагружает Python-процессы.

**Плохо:** ещё один контейнер и ещё один источник «частично записанного» состояния.
Компенсируется порядком: сначала объект в S3, потом строка в БД; «сирота» в S3 безвреден,
строка без файла — нет.

## Альтернативы

- **`bytea` в PostgreSQL.** Раздувает базу и бэкапы, убивает производительность на выборках.
- **Локальный том.** Проще, но не масштабируется на много камер и требует общего диска
  для реплик воркера; presigned-ссылок нет, картинки пришлось бы проксировать.
