# ADR-0008. LLM только для текста, никогда для чисел

**Статус:** принято, 17.09.2026

## Контекст

ТЗ допускает LLM поверх план-факта для ранних предупреждений и резюме. Главный риск
очевиден: модель придумает число, оно попадёт в отчёт заказчику, и доверие к системе
кончится в одну секунду — на глазах у жюри.

## Решение

1. LLM получает **только структурированный JSON-контекст**: статус объекта, этапы с SPI
   и прогнозом, отклонения с их ID и `facts`. Никаких свободных данных, никаких снимков.
2. Задача модели — связный русский текст для руководителя со **ссылками на ID отклонений**.
3. После генерации выполняется проверка: **каждое число из текста должно встречаться
   в контексте**. Не прошло — текст отбрасывается, выдаётся шаблонное резюме.
4. `LLM_ENABLED=false` или таймаут → сразу шаблонное резюме. Демонстрация от LLM не зависит.
5. Все числа на экранах и в отчётах приходят из `analysis-service`, а не из текста резюме.

## Последствия

**Хорошо:** галлюцинация не может изменить ни одну цифру в отчёте; продукт работает
без интернета и без GPU; на вопрос жюри «а если модель наврёт?» есть короткий и
проверяемый ответ.

**Плохо:** текст беднее, чем мог бы быть при свободном доступе к данным. Осознанная плата.
Проверка чисел — эвристика (сравнение числовых токенов), она может отбросить корректный
текст с округлением; в этом случае пользователь получает шаблонное резюме, что безопасно.

## Альтернативы

- **LLM как аналитик поверх сырых данных.** Эффектно на демо, катастрофично в эксплуатации
  бюджетного объекта.
- **Без LLM вообще.** Надёжно, но теряется требование F12 и заметная часть впечатления.
