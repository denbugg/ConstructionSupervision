# ADR-0012. Факт без оценок: site описывает, analysis оценивает

**Статус:** принято, 23.09.2026. Уточняет [ADR-0002](0002-service-boundaries.md): меняет
агрегирующие эндпоинты и распределение выводов между сервисами.

## Контекст

По прежним документам граница «факт / сверка» протекала.

- `site-service` определял, попадает ли сессия в рабочее время. Для этого нужен календарь
  объекта, а он живёт в `plandb`.
- `site-service` определял статус «работает / простой в активной зоне». Для этого нужен
  график, а в `plan-service` site не обращается.
- Ключевой контракт «план на дату» возвращал только активные этапы. Но для D3 нужны правила
  будущих этапов, для D8 — этапы после планового окончания, для прогноза — весь граф связей.
- Факты забирались по одному запросу на сессию: около сотни запросов на прогон.
- Сессия закрывалась по таймеру после окончания окна. При импорте прошлых дней таймер не
  имеет смысла.
- «Сегодня» в формулах означало время на часах. На демо с историческими днями это даёт
  нулевой плановый прогресс или фиктивное отставание.

## Решение

1. **site отдаёт только наблюдения:** участок, класс, количество, неподвижность, видимость,
   стадия по фото, снимки-доказательства. Рабочее время, статус техники, отклонения,
   прогресс и прогноз вычисляет только `analysis-service`, потому что только у него есть
   и план, и факт.
2. **Два контракта вместо «план на дату» и «факт по сессии»:** весь план объекта одним
   запросом и факты за период одним запросом
   ([packages/contracts/interservice.md](../../packages/contracts/interservice.md)).
3. **Сессия — окно 30 минут без статусов.** Факт окна пересчитывается после каждого
   обработанного снимка этого окна. Таймера закрытия и ожидания опоздавших снимков нет.
4. **Прогон считается на момент `as_of`.** По умолчанию это конец последней сессии с
   фактами. Сигналы «пересчитай» от site и plan схлопываются: на объект идёт не больше
   одного прогона, и после него — не больше одного повторного.

## Последствия

**Хорошо:**
- Граница «план / факт» снова чистая: site не зависит от плана.
- Вся методика собрана в одном сервисе, и её можно прогнать на фикстурах.
- Импорт прошлых дней и живой поток обрабатываются одинаково.
- Каждый прогон — два запроса, а не сотня.

**Плохо:**
- analysis может увидеть неполное окно до прихода остальных снимков. Это безопасно:
  участок без пригодного кадра считается невидимым, а не пустым, поэтому ложного D1 не будет.
  Поздний снимок пересчитает окно, и следующий прогон исправит вывод.
- Ответ «факты за период» за несколько месяцев получается крупным. Если это станет
  проблемой, прогон будет запрашивать факты окнами. Контракт это уже допускает.

## Альтернативы

- **Оставить оценки в site и дать ему доступ к plan.** Появляется связь site → plan, и план
  протекает в факт. Граница, ради которой сервисы разделены, исчезает.
- **Оставить «план на дату» и добавить к нему запросы будущих и просроченных этапов.**
  Три контракта вместо одного, и каждый со своими крайними случаями.
