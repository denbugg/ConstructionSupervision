# Правила написания кода и документации

Короткая сводка — в [CONTRIBUTING.md](../CONTRIBUTING.md), раздел 8–9. Здесь подробности и примеры.
Цель правил одна: **чужой сервис должен читаться как свой**. Тогда любой участник может войти
в любую часть системы без разогрева.

---

## 1. Общие принципы

1. **Простое решение по умолчанию.** Абстракция вводится, когда у неё уже есть два реальных
   применения, а не когда «может пригодиться». Базовый класс с одним наследником, фабрика
   с одним продуктом, интерфейс с одной реализацией — это усложнение, а не архитектура.
2. **Явное лучше умного.** Пять понятных строк лучше одной с тремя вложенными comprehension.
   Код читают в десять раз чаще, чем пишут, а у нас на всё полторы недели.
3. **Одна функция — одна мысль.** Если в докстринге приходится писать «и», функцию надо делить.
4. **Ошибка должна быть громкой.** Пустой `except`, значение по умолчанию вместо исключения
   и «тихий» пропуск данных — прямой путь к неверным выводам в отчёте заказчику.
5. **Никаких сюрпризов.** Функция не должна делать того, чего не обещает имя: `get_*` не пишет
   в БД, `validate_*` не отправляет письма.

## 2. Структура Python-сервиса

Одинаковая во всех сервисах. Зависимости направлены строго внутрь: `api → services → core`,
а `dal` и `clients` подключаются к `services`, но не к `core`.

```text
src/
├── main.py          # создание FastAPI, подключение роутеров, middleware, lifespan
├── config.py        # Settings (pydantic-settings) — единственное место чтения окружения
├── api/
│   ├── routes/      # роутеры: валидация → вызов services → маппинг ошибок в HTTP
│   ├── schemas/     # Pydantic DTO (контракт наружу; НЕ переиспользуются как модели БД)
│   └── deps.py      # зависимости FastAPI: сессия БД, клиенты, проверка API-ключа
├── core/            # ЧИСТАЯ доменная логика: формулы, правила, алгоритмы
├── dal/
│   ├── models.py    # SQLAlchemy-модели
│   └── repositories/# запросы; единственное место, где есть SQL
├── clients/         # HTTP-клиенты к другим сервисам; единственное место с httpx
├── services/        # сценарии использования: собрать данные, вызвать core, сохранить
└── worker.py        # фоновые задачи (только там, где они есть)
```

| Слой | Можно | Нельзя |
| :--- | :--- | :--- |
| `api/` | Валидировать вход, звать `services`, переводить доменные ошибки в HTTP | Считать, ходить в БД, звать другие сервисы |
| `services/` | Оркестрировать: репозитории, клиенты, `core`, транзакции | Содержать формулы и правила |
| `core/` | Чистые функции и датаклассы, детерминированный расчёт | Импортировать SQLAlchemy, httpx, FastAPI |
| `dal/` | SQL, маппинг строк в модели | Бизнес-правила |
| `clients/` | HTTP наружу, таймауты, ретраи, перевод чужих ошибок | Бизнес-решения на основе ответа |

**Почему `core` обязан быть чистым:** это то, что мы показываем жюри и тестируем за секунды
без докера. Как только в правило просачивается запрос к БД, его нельзя ни объяснить, ни
воспроизвести.

## 3. Python: конкретика

**Версия и инструменты:** Python 3.12, `ruff` (линт + формат), `pytest` + `pytest-asyncio`.
`mypy` пока не подключён — появится вместе с `tools/mypy.ini` и джобом в CI.

Настройки линтера живут **только** в [`tools/ruff.toml`](../tools/ruff.toml) — один файл
на весь репозиторий. В `pyproject.toml` сервиса секции `[tool.ruff]` быть не должно:
два источника правил расходятся в первый же день, и «у меня линт проходит» перестаёт
что-либо значить. Нужно исключение — оно добавляется в общий файл с обоснованием.

**Асинхронность.** Весь ввод-вывод асинхронный: `async def` эндпоинты, `AsyncSession`
SQLAlchemy, `httpx.AsyncClient`. Блокирующий вызов (inference, WeasyPrint, работа с файлом)
уходит в `anyio.to_thread.run_sync` или в воркер. Смешивание sync-драйвера с async-приложением
запрещено.

**Типы.** Обязательны в сигнатурах публичных функций. Внутренние переменные — по необходимости.
`Any` допускается только на границе с чужим нетипизированным JSON и сразу приводится
к Pydantic-модели.

**Именование.**

| Сущность | Стиль | Пример |
| :--- | :--- | :--- |
| Модуль, функция, переменная | `snake_case` | `equipment_state.py`, `resolve_zone` |
| Класс, Pydantic-модель | `PascalCase` | `SessionFacts`, `DeviationRule` |
| Константа | `SCREAMING_SNAKE` | `MIN_ACTIVITY` |
| Булево | утверждение | `is_critical`, `has_signature` |
| Функция-вопрос | `is_/has_/can_` | `has_required_equipment()` |
| Функция-действие | глагол | `compute_forecast()`, `assign_zone()` |

Сокращения запрещены, кроме общепринятых: `id`, `url`, `db`, `api`, `cv`, `bbox`, `spi`.
Никаких `mgr`, `proc`, `tmp2`, `data2`.

**Ошибки.**

```python
# core/ и services/ бросают доменные исключения
class StageRuleNotFound(DomainError):
    code = "STAGE_RULE_NOT_FOUND"

# api/ переводит их в HTTP единообразно, через общий обработчик из py-common
```

Запрещено: `except Exception: pass`, `except:` без класса, возврат `None` вместо исключения
в ситуации «данных нет, но должны быть», исключения как поток управления в нормальном сценарии.

**Логи.** Только структурный логгер из `py-common`:

```python
log.info("facts.updated", session_id=str(session.id), areas=len(facts), duration_ms=41)
```

Событие — точка (`domain.action`), остальное — поля. Никаких f-строк в сообщении,
никакого `print`, никаких персональных данных и содержимого конфигурации в логах.

**Конфигурация.** Единственное место чтения окружения — `config.py`:

```python
class Settings(BaseSettings):
    session_window_minutes: int = 30
    vision_url: AnyHttpUrl
    vision_timeout_s: float = 30.0
```

`os.environ` где-либо ещё — ошибка. Значение по умолчанию обязано быть безопасным
и пригодным для локального запуска.

**Перечисления и классы техники.** Значения берутся из `packages/contracts/enums.yaml` и
`equipment_classes.yaml` (путь — `settings.contracts_dir`). Единственное место, где список
значений допустимо повторить в коде, — CHECK-ограничения в `dal/models.py` и миграциях: СУБД
не умеет читать YAML. Тест сервиса сверяет эти списки с `enums.yaml`, чтобы они не разъехались.

**Скрипты.** Всё в `scripts/` пишется на Python, а не на bash: демо-стенд работает на Windows,
где bash нет.

**Размеры.** Функция ≤ 50 строк, файл ≤ 400 строк, вложенность ≤ 3 уровней,
аргументов ≤ 5 (дальше — датакласс). Это ориентиры: превышение не запрещено, но требует
осознанного ответа на вопрос «почему».

## 4. TypeScript и React

**Стек:** TypeScript 5 (`strict: true`), React 18, Vite, TanStack Query, Tailwind,
`react-hook-form` + `zod` для форм, сгенерированный клиент из `packages/ts-api-client`.

```text
apps/web/src/
├── app/           # роутер, провайдеры, layout, обработка ошибок
├── features/      # экраны и их логика: dashboard, gantt, deviations, cameras, zones, …
├── entities/      # доменные типы, мапперы, форматтеры (дата, SPI, серьёзность)
├── shared/
│   ├── api/       # обёртка над сгенерированным клиентом, перехват ошибок
│   ├── ui/        # переиспользуемые компоненты
│   ├── lib/       # хуки и утилиты
│   └── locale/ru.ts  # общие строки: перечисления, ошибки, единицы
└── main.tsx
```

Правила:

- `any` запрещён; типы ответов API берутся только из сгенерированного клиента и не дублируются;
- компонент — отображение: вычисления, агрегации и форматирование живут в хуках и `entities/`;
- серверное состояние — только через TanStack Query (кэш, инвалидация, повтор),
  локальный `useState` — только для состояния интерфейса;
- интерфейс только на русском, поэтому строки экрана пишутся прямо в JSX; в
  `shared/locale/ru.ts` — только общие строки: названия перечислений, тексты ошибок, единицы;
- никаких инлайновых стилей и магических чисел в классах — только токены Tailwind;
- ошибки API показываются пользователю тем самым `message`, который вернул сервис,
  плюс `request_id` мелким шрифтом — это резко ускоряет разбор на демо;
- состояния «загрузка», «пусто», «ошибка» обязательны для каждого экрана: пустой экран
  без объяснения — дефект.

## 5. Комментарии

**Комментарий объясняет причину, а не действие.**

```python
# плохо — пересказ кода
# берём максимум по камерам
count = max(per_camera_counts)

# хорошо — причина решения
# Максимум, а не сумма: зоны камер физически пересекаются, и одна машина
# попадает в кадр с двух сторон. Сумма дала бы двойной счёт (см. methodology.md, п.5).
count = max(per_camera_counts)
```

**Комментарий обязателен там, где:**

- используется норматив или число из документа — со ссылкой на пункт и таблицу последней
  редакции: `# МРР-3.2.81, п. X.Y, табл. N: коэффициент для монолитного исполнения`;
- сделано приближение или принято допущение — с указанием, чем оно оправдано;
- поведение неочевидно из имени (порядок проверок, граничный случай, защита от деления на ноль);
- код реализует требование ТЗ — ссылка на его идентификатор (`F4`, `D7`).

**Комментарий запрещён там, где:**

- он повторяет имя функции или сигнатуру;
- это закомментированный код (удаляем: история есть в git);
- это баннер-разделитель `# ====== helpers ======`;
- это `TODO` без автора и контекста. Допустимо: `# TODO(имя, до 24.09): вынести пороги в БД`.

**Докстринги.**

```python
def compute_forecast(stage: StagePlan, activity: Sequence[DailyActivity]) -> Forecast:
    """Прогноз окончания этапа по среднему темпу последних рабочих дней (F9).

    Темп берётся за 5 последних рабочих дней; при среднем индексе ниже MIN_ACTIVITY
    прогноз считается по MIN_ACTIVITY и помечается confidence=LOW, иначе прогноз
    уходил бы в бесконечность при полном простое.
    """
```

Модуль открывается одной строкой о его назначении и ссылкой на требование ТЗ:

```python
"""Правила выявления отклонений D1–D10 (ТЗ, п. 5.3). Чистые функции, без ввода-вывода."""
```

Язык: **комментарии и докстринги — русские**, идентификаторы — английские.
Проект сдаётся московскому заказчику, документацию будут читать по-русски.

## 6. Документация в репозитории

| Документ | Кто обновляет | Когда |
| :--- | :--- | :--- |
| `services/<name>/README.md` | Автор изменения | В том же коммите, если изменился контракт, модель данных или конфигурация |
| `docs/data-model.md` | Автор миграции | В том же коммите |
| `docs/methodology.md` | Автор правила или формулы | До реализации: сначала описываем методику, потом кодируем |
| `docs/traceability.md` | Автор изменения | При закрытии требования ТЗ |
| `docs/decisions/` | Тот, кто принимает решение | До реализации |
| `README.md` в корне | По необходимости | При изменении состава сервисов или способа запуска |

**README сервиса имеет фиксированную структуру** (нарушать нельзя: по ней ищут нужное во всех сервисах сразу):

1. Назначение — 2–3 предложения;
2. Место в системе — кто вызывает, кого вызывает;
3. API — таблица эндпоинтов + примеры запроса и ответа для ключевых;
4. Модель данных — таблицы и их смысл (ссылка на `docs/data-model.md` за подробностями);
5. Конфигурация — таблица переменных окружения со значениями по умолчанию;
6. Зависимости — сервисы и инфраструктура;
7. Запуск и тесты;
8. Допущения и ограничения — честный список того, что не работает или работает приближённо.

**ADR** (`docs/decisions/NNNN-имя.md`) — короткий документ по шаблону:
`Статус → Контекст → Решение → Последствия → Рассмотренные альтернативы`.
Принятый ADR не переписывается: если решение изменилось, пишется новый со статусом
«отменяет ADR-NNNN».

## 7. Git

- Ветка: `feat/<service>-<кратко>`, `fix/<service>-<кратко>`, `docs/<кратко>`, `chore/<кратко>`.
- Коммит — Conventional Commits, область = сервис:

```
feat(analysis): предикаты D8 и D9 по фактическому старту этапа
fix(site): не терять снимки без EXIF, переводить в статус NEEDS_TIME
docs(adr): 0007 — правила отклонений как данные
refactor(plan): вынести CPM в core, убрать обращение к БД из расчёта
```

- Один коммит — одно изменение. Рефакторинг и новая функциональность — разные коммиты.
- Сообщение — по-русски, в повелительном или назывном стиле, без «fix bug» и «update».
- В `.gitignore`: `.env`, `data/models/*`, датасеты, `node_modules/`, `__pycache__/`,
  `*.pyc`, `.venv/`, `dist/`, выгрузки и отчёты.

## 8. Чек-лист перед тем, как сказать «готово»

- [ ] `make lint` и `make test` зелёные;
- [ ] логика из `core/` покрыта тестами, включая граничные случаи;
- [ ] нет новых захардкоженных порогов, URL и названий классов;
- [ ] README сервиса и, при необходимости, `docs/` обновлены в этом же изменении;
- [ ] `make contracts` выполнен, если менялся API;
- [ ] сервис поднимается в `docker compose` и отвечает на `/health/ready`;
- [ ] в логах нет `print`, в коде нет закомментированных блоков и мусорных `TODO`.
